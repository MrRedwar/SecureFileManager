## 0. Источники и границы договорённостей

**Из методического задания «Семестровое задание №1.pdf», с. 1–3:** файловый менеджер, просмотр дисков, чтение/запись/удаление файлов, JSON/XML, создание/извлечение ZIP, реляционная база с данными о файлах и операциях, журнал активности. Рекомендованы аутентификация с хешированием паролей, SQL-подготовленные запросы, безопасная десериализация и ограничения распаковки. В качестве СУБД прямо перечислены PostgreSQL/MySQL/SQLite; указан формат «консольное или клиент-серверное приложение».

**Утверждённые проектные решения:** настольный WPF UI, C#, архитектура MVVM, Microsoft SQL Server как начальная СУБД, Entity Framework Core, мягкая тема Древнего Египта, рабочая область файлов и отдельный слой данных. Основа — `Secure_File_Manager_Финальный_план_разработки.docx`, согласованный в обсуждении; здесь решения уточняются до проверяемого поведения.

**Требует согласования с преподавателем:** допустимость WPF-клиента без отдельного прикладного сервера и использование Microsoft SQL Server вместо перечисленных СУБД. Подключение WPF напрямую к SQL Server технически является клиент-серверным взаимодействием на уровне БД, но **не обязательно** соответствует ожидаемой преподавателем архитектуре. Не выдавать этот вопрос за решённый.

**Технические параметры ниже (лимиты, поля, последовательности, шрифты и т. п.)** — проектные предложения, а не дословные требования методички. Менять их только согласованным изменением данного ТЗ.

## 1. Цель, результат и границы

### 1.1. Назначение
Создать локальное Windows-приложение **Secure File Manager** для управления собственными файлами пользователя в выделенной защищаемой рабочей области. Предоставить средства просмотра характеристик дисков, редактирования текстовых/JSON/XML-файлов, архивации ZIP, регистрации действий и проверки прав.

### 1.2. Обязательная область реализации (MVP/сдача)
- WPF-окна регистрации, входа, главное окно и разделы «Диски», «Мои файлы», «Архивы», «JSON / XML», «Журнал», «Настройки».
- Отображение характеристик доступных дисков; просмотр файлов и каталогов в собственной рабочей области.
- Создание, чтение, изменение, сохранение и удаление файлов; создание папок для удобной навигации.
- Работа с TXT, JSON и XML; проверка синтаксиса и безопасная обработка.
- Создание ZIP, предварительный просмотр состава, безопасная распаковка.
- Регистрация/вход пользователей, защита паролей и разграничение владения файлами.
- Реляционная БД: `Users`, `Files`, `Operations`, сведения и журнал операций.
- Негативные проверки на SQL injection, Path Traversal, XXE, ZIP Slip/ZIP Bomb, чужие файлы и ошибки ввода.
- Инструкция запуска, тестовые данные и демонстрационные сценарии.

### 1.3. Не входит в первую версию
- Подключение к облачным хранилищам; сетевое файловое хранилище; серверное REST API, если преподаватель не потребует.
- Просмотр/редактирование произвольных папок Windows вне выделенного корня; операции с системными файлами.
- Сложная ролевая иерархия, обмен файлами между пользователями, админ-панель для чтения чужих данных.
- Поддержка 7z/RAR, бинарного редактора, шифрование файлов «на диске», сложные анимации.
- Обещание противостоять локальному администратору ОС или злоумышленнику с прямым доступом к БД и диску.

## 3. Пользователи и модель безопасности

### 3.1. Роли и владение
- Каждому пользователю присваивается `User.Id` (GUID либо int; окончательный тип фиксируется в модели и используется везде единообразно). У него своя физическая рабочая область `Storage/Users/<user-id>/`.
- Пользователь может просматривать, читать, создавать, изменять и удалять **только собственные** файлы и папки в пределах своего корня.
- «admin» в макете — пример имени пользователя, **не** системная роль и не право читать чужие данные.
- Просмотр журнала — только собственные события. Системную роль администратора в MVP не вводить.
- Страница «Диски» выдаёт read-only характеристики накопителей, но не даёт доступ к произвольным OS-путям для операций.
- Прямой доступ к физическим файлам/БД со стороны привилегированного пользователя ОС не рассматривается как защищённая граница WPF-клиента. Обязательно оговорить это в отчёте.

### 3.2. Аутентификация
- Регистрация: уникальный логин 3–50 символов, пароли минимум 10 и максимум 128 символов; поля пароля скрыты; одинаковые имена не допускаются по установленной в БД политике регистра (выбрать и документировать).
- Пароли хранятся только в виде хеша с солью (например, адаптер для `PasswordHasher<TUser>` с PBKDF2 и версионированием параметров); plaintext-пароли не сохраняются и не логируются. Пароли и секреты не показываются в сообщениях исключений.
- При входе недопустимые данные обрабатываются без падения; сообщение «Неверный логин или пароль» не позволяет узнать, существует ли учётная запись.
- Защита от перебора: счётчик неудачных попыток и кратковременная блокировка после 5 ошибок в течение 15 минут, с сообщением пользователю без утечки секретов; реализовать проверяемо (параметризованная политика). Не рассчитывать на неё как на защиту от доступа к файлу БД напрямую.
- Текущий пользователь хранится в памяти сессии приложения; выход очищает сессию и закрывает чувствительные окна.

## 4. Функциональные требования (FR)

### FR-01. Запуск и навигация
1. При запуске проверяется конфигурация и доступность БД. Если БД недоступна, показывается диагностическое сообщение и предлагается повторить подключение или закрыть приложение; операции с файлами не допускаются без аудита/проверок.
2. После входа открывается главное окно. Левая навигация: «Диски», «Мои файлы», «Архивы», «JSON / XML», «Журнал», «Настройки».
3. Переходы не разрушают несохранённые изменения без подтверждения. Текущий пользователь указан в футере.
4. Кнопки имеют понятные недоступные состояния и подсказки. Отображение ошибок не раскрывает стек трассировки/пароли/строку подключения.

### FR-02. Список дисков
- Использовать `DriveInfo.GetDrives()` с обработкой отсутствующих/неготовых дисков (`IsReady`).
- Для готового диска выводить имя, тип, формат ФС, общий и свободный объём, процент использования; для неготового — понятный статус.
- Эта страница **только для чтения** и не обходит границы пользовательского хранилища.

### FR-03. Файлы и каталоги
- **Уточнение этапа 05 от 02.11.2026 по явному поручению пользователя:** импорт одного выбранного локального файла — узкое исключение чтения внешнего источника. Источник только копируется в собственное хранилище, не перемещается/удаляется и не становится доступным внешним расположением. Проверяются Windows ACL, ссылки, конфликты и назначение; UNC/network/device/ADS, ярлыки и источники внутри Storage не допускаются. Лимит импорта — 100 МиБ фактически записанных байтов, TXT — 10 МиБ. Это не режим B. Обоснование и протокол — `docs/FILE_OPERATIONS.md` и `docs/DECISIONS.md`.
- Корень хранения конфигурируется для приложения и создаётся при первой инициализации; внутри него отдельные пользовательские директории.
- Показывать содержимое текущей папки (имя, тип, размер, дата изменения), хлебные крошки; разрешить переход только по разрешённым дочерним каталогам, возврат к своему корню.
- Создание текстового файла: пользователь задаёт имя/расширение, программа проверяет допустимость, права, отсутствие конфликта и корректность пути. Не перезаписывать существующий файл без отдельного подтверждённого сценария.
- Создание папки: аналогичные проверки, недопустимые имена и ссылки не разрешены.
- Чтение/открытие: файл принадлежит пользователю, расположен в разрешённом корне, не является запрещённым типом ссылки; открыть редактор, если формат поддержан, иначе показать метаданные и понятное сообщение.
- Изменение: редактор помечает содержимое как несохранённое; `Сохранить` пишет данные без неконтролируемой частичной порчи исходного файла; после успеха метаданные синхронизированы.
- Удаление: предварительное подтверждение; файл/папка удаляется только после авторизации, операции журналируются; на первом этапе удаление **непустого каталога** запрещено, пользователь должен удалить содержимое отдельно.
- Поиск/сортировка — в пределах текущей папки/собственного дерева; никаких запросов к произвольным каталогам ОС.
- Типичные ошибки (не найден, доступа нет, занят другим процессом, повреждён, конфликт имени, нехватка места) отображаются информативно и без падения UI.

### FR-04. TXT, JSON и XML
- Текстовый редактор: UTF-8 по умолчанию; открытие/сохранение TXT, JSON, XML; признак несохранённого содержимого, подтверждение закрытия.
- JSON через `System.Text.Json`: корректная сериализация/десериализация в контролируемую модель или `JsonDocument`, без создания произвольных типов по входным метаданным; проверка синтаксиса до сохранения JSON.
- XML через `System.Xml`: отключить DTD и внешние сущности, не обращаться к сетевым ресурсам; проверять корректность документа и лимиты.
- Для исходного JSON/XML разрешено форматирование (если безопасно), но оно не должно silently менять файл: только после действия пользователя и сохранения.
- Ограничение размера файла редактора по умолчанию **10 МиБ** (настраивается); более крупный файл не загружать целиком в UI, показать ясное сообщение.
- Ошибка проверки — редактор остаётся открытым, выводится описание и, если возможно, строка/позиция; сохранять некорректный JSON/XML через профильный редактор нельзя (изменение стандартного TXT от этого не зависит).

### FR-05. ZIP
- Создание архива: пользователь выбирает допустимые файлы и/или каталоги **только своего хранилища** и путь назначения также только внутри него. Поддерживаются выбор одного или нескольких объектов и предотвращение упаковки архива самого в себя.
- До распаковки отображается список записей архива и сводка: число элементов, суммарный незапакованный размер, потенциальные риски.
- Распаковка проводится **только в разрешённый каталог**, с запретом абсолютных путей, `..`, дисковых префиксов, ссылок, некорректных имён, выходов за корень и конфликтов назначения. Запись в существующий файл — запрет по умолчанию.
- Учебные защитные лимиты по умолчанию: не более **250 записей**, **25 МиБ на запись**, **100 МиБ суммарно после распаковки**, **100:1** максимально допустимое отношение распакованного объёма к сжатому для ненулевого сжатого размера. Эти величины — **проектные значения**, а не требования PDF; все лимиты проверяются по фактически записанным байтам во время потоковой распаковки, а не только по заголовкам ZIP. Нулевой сжатый размер при ненулевом распакованном — отклонять.
- Потоковая распаковка с ограничениями, отменой и очисткой временного каталога при неудаче; на успешном финале — перенос в разрешённое назначение с проверкой конфликтов.
- Любой отказ и успешная операция фиксируются в аудите; UI остаётся отзывчивым во время работы.

### FR-06. База данных
- `Users`, `Files`, `Operations` — обязательные сущности; содержимое пользовательского файла **остаётся на диске**, БД хранит метаданные и историю.
- Изменение данных только через слой `SecureFileManager.Data` (EF Core и контракт репозиториев). Запрет SQL-конкатенации из пользовательского ввода; LINQ или параметризованный SQL.
- Миграции применяются контролируемо: не удалять и не пересоздавать БД с существующими данными «для исправления» без явного согласования.
- Записи удалённых файлов **не должны уничтожать историю действий**: использовать `Files.IsDeleted` и `Operations.TargetPathSnapshot`.
- При смене СУБД поменять провайдер, настройки, провайдерские миграции и тесты совместимости; данные мигрируют отдельной процедурой, автоматическую бесшовную замену не обещать.

### FR-07. Журнал действий
- События: `LOGIN_SUCCESS`, `LOGIN_FAILED`, `LOGOUT`, `FILE_CREATED`, `FILE_READ`, `FILE_UPDATED`, `FILE_DELETED`, `DIRECTORY_CREATED`, `JSON_VALIDATED`, `XML_VALIDATED`, `ZIP_CREATED`, `ZIP_EXTRACTED`, `ACCESS_DENIED`, `OPERATION_FAILED`.
- Для события сохранять UTC-время, инициатора (ID при наличии; имя введённого логина при ошибке входа — без пароля), вид операции, целевой относительный путь/снимок, статус (`Success`/`Denied`/`Failed`), краткое безопасное описание. `FileId` допускает NULL.
- В таблице можно фильтровать по дате, типу, статусу; обычный пользователь видит собственные события. Для ошибки входа без `UserId` запись сохраняется в БД, но глобальный просмотр всех таких записей из пользовательского UI не предоставляется.
- Аудит **не должен заявлять успех**, пока операция не завершена; отказ в доступе фиксируется независимо от успешности модификации файла.
- При недоступности БД пользовательские файловые операции блокируются, чтобы не выполнять изменения без учёта и аудита. Если журнал всё же недоступен после частичного файлового действия — показать ошибку согласованности и выполнить предусмотренное восстановление/сверку.

### FR-08. Настройки
- Отображать текущего пользователя, путь его рабочей области (только для чтения), версию приложения, лимиты редактора/ZIP, состояние БД.
- Не позволять пользователю расширять область доступа произвольным выбором нового корня через UI. Изменения root/storage — через конфигурацию приложения под контролем разработчика.

## 5. Модель данных (проектные поля)

### Users
| Поле | Тип/смысл | Ограничение |
|---|---|---|
| `Id` | PK | неизменяемый идентификатор |
| `Username` | имя входа | required, unique, max 50 |
| `PasswordHash` | хеш с солью и параметрами | required; никогда plaintext |
| `CreatedAtUtc` | время создания | UTC, required |
| `IsActive` | активен | default true |
| `FailedLoginCount` | число неудачных попыток | неотрицательное |
| `LockoutUntilUtc` | окончание блокировки | nullable |

### Files
| Поле | Тип/смысл | Ограничение |
|---|---|---|
| `Id` | PK | required |
| `OwnerId` | FK → Users | required, индекс |
| `Name` | имя | required |
| `RelativePath` | путь **от корня пользователя** | required, уникальность `(OwnerId, RelativePath)` среди актуальных объектов; учесть soft-delete |
| `Kind` | File/Directory | required |
| `Extension` | расширение (для файлов) | optional |
| `SizeBytes` | размер | >= 0 |
| `CreatedAtUtc`, `ModifiedAtUtc` | даты | UTC |
| `IsDeleted`, `DeletedAtUtc` | мягкое удаление | флаг + время |

### Operations
| Поле | Тип/смысл | Ограничение |
|---|---|---|
| `Id` | PK | required |
| `UserId` | FK → Users, nullable | NULL для неизвестного неудачного логина |
| `ActorNameSnapshot` | логин инициатора | без секрета |
| `FileId` | FK → Files, nullable | для входов/ошибок/неизвестного файла |
| `OccurredAtUtc` | время события | UTC |
| `OperationType` | тип операции | required |
| `Result` | Success/Denied/Failed | required |
| `TargetPathSnapshot` | относительный путь | без абсолютного системного секрета |
| `Details` | краткий код/описание | без тела файла и персональных секретов |
| `CorrelationId` | ID сценария | для трассировки сложных операций |

**Индексы:** `Users.Username` unique; `Files.OwnerId`, `(OwnerId, RelativePath, IsDeleted)` с корректной политикой уникальности; `Operations.UserId, OccurredAtUtc`, `Operations.OperationType, Result`. Для soft-delete пересоздание пути допускается при истории старого файла; алгоритм определения активного файла обязан учитывать `IsDeleted=false`. EF Core миграции выбирают соответствующие ограничения для SQL Server и, позже, для других провайдеров.

**Зависимости:** Wpf → Core, Wpf → Data **только в composition root/регистрации DI**; Data → Core. Core **не зависит** от WPF, EF Core или SQL Server. Views не выполняют SQL и не читают файлы напрямую. ViewModels вызывают прикладные сервисы через интерфейсы и не содержат платформенно-специфичной проверки пути. Внедрение зависимостей — Microsoft.Extensions.DependencyInjection/Host при необходимости.

**Интерфейсы (проектные):** `IAuthenticationService`, `IUserRepository`, `IFileRepository`, `IOperationRepository`, `IAuditService`, `IFileService`, `IDriveService`, `IFormatService`, `IArchiveService`, `IPathPolicy`, `IClock`. Возвращать типизированные результаты (`Success`, `Validation`, `Unauthorized`, `NotFound`, `Conflict`, `InfrastructureError`) вместо обработки исключений в каждом окне; исключения логировать без утечки секретов.

**Операции файловой системы + БД:** общей атомарной транзакции нет. Применять временные файлы, предвалидацию, фиксированный порядок действий, компенсационные шаги и сервис сверки. На исключении не заявлять успешное завершение; выводить состояние «операция не завершена» или «требуется сверка»; создать тест для сбоя после записи файла и до сохранения метаданных.

## 7. Сквозные требования безопасности (SEC)

| ID | Угроза | Требуемое поведение | Проверка |
|---|---|---|---|
| SEC-01 | SQL injection | EF Core LINQ / параметризация, никакой пользовательской строки в SQL-структуре | ввод `' OR 1=1 --` не изменяет логику |
| SEC-02 | Path Traversal | назначения и обычные операции только в пользовательском корне; единственное исключение — чтение явно выбранного источника импорта согласно FR-03. Для назначений запрещены `..`, абсолютные внешние пути, недопустимые имена, reparse points/симлинки в зоне операций | `../`, `..\\`, абсолютный путь и ссылка отклонены |
| SEC-03 | Превышение прав | каждая операция проверяет authenticated `OwnerId` и физическую границу; проверки в сервисе, не только кнопках | User B не читает и не меняет файл User A |
| SEC-04 | XXE | DTD/внешние сущности запрещены, XML resolver не открывает файлы/сеть | XML с DOCTYPE отвергнут |
| SEC-05 | ZIP Slip | отвергаются любые записи вне корня, абсолютные/дисковые пути и ссылки | `../../outside.txt` не создаётся |
| SEC-06 | ZIP Bomb | лимит числа записей, фактических байтов и коэффициента распаковки | срабатывает ограничение, временные файлы удаляются |
| SEC-07 | Пароли | соль, адаптивный KDF, безопасная проверка, нет plaintext и утечек | DB содержит хеш; логин работает |
| SEC-08 | Race conditions | не полагаться только на `Exists`+`Open`; использовать безопасные режимы открытия, повторные проверки, временные файлы; ACL защищают рабочую область | конкурентные создания/изменения корректно обрабатываются |
| SEC-09 | Audit | успех/отказ/ошибка фиксируются с правильным статусом; недоступная БД не разрешает неаудируемые изменения | аудит T14, тест сбоя БД |
| SEC-10 | Секреты/исключения | no passwords/connection secrets/текст документов в журналах, трассировки только в dev | поиск секретов и ошибочные сценарии |

**Ограничение модели угроз:** настольное приложение не защищает от привилегированного локального пользователя или пользователя с обходным прямым доступом к SQL Server/Storage; для строгой многопользовательской безопасности потребуется серверная проверка доступа и системные ACL. На учебном уровне права на папки и SQL-учётную запись ограничить настолько, насколько позволяет развёртывание. Не заявлять более сильную гарантию.

## 8. Нефункциональные требования (NFR)

- **NFR-01, отзывчивость:** UI не зависает при операциях ZIP/файлах; длинные операции асинхронны, имеют индикатор прогресса и по возможности отмену.
- **NFR-02, устойчивость:** ошибочный файл, недоступный диск, неправильный XML, сбой SQL не приводят к необработанному исключению на основном UI-потоке.
- **NFR-03, локализация:** пользовательские подписи и ошибки на русском; технические идентификаторы в коде на английском.
- **NFR-04, доступность:** клавиатура, видимый фокус, читаемый контраст, стандартный масштаб Windows; управление при 125–200% DPI.
- **NFR-05, переносимость СУБД:** SQL Server ограничен инфраструктурным слоем; отдельные миграции при новом провайдере.
- **NFR-06, данные:** UTC в БД, локальное время в UI, значения размера в КиБ/МиБ/ГиБ с единообразным округлением.
- **NFR-07, диагностика:** безопасные ошибки для пользователя, подробности для локальной отладки без секретов.
- **NFR-08, воспроизводимость:** новая установка по инструкции создаёт БД и рабочую папку без ручной правки исходников.

## 9. Пользовательские сценарии и результат

**UC-01: создание файла** → авторизован → «Мои файлы» → «Создать» → имя и тип → проверки/конфликт → безопасное создание → строка в Files → успешная запись в Operations → обновлённый список. При ошибке: файл/метаданные не должны silently расходиться; пользователь получает статус.

**UC-02: изменение JSON** → открыть `*.json` → редактировать → «Проверить» → показать синтаксические ошибки или успех → «Сохранить» → метаданные/журнал. Некорректный JSON не сохраняется профильным редактором.

**UC-03: распаковка архива** → выбрать ZIP → показать содержимое и проверку границ/лимитов → выбрать своё назначение → потоковая распаковка в staging → финальная проверка/перенос → журнал и список. При нарушении: отмена и очистка staging, отказ и аудит.

**UC-04: отказ доступа** → User B пытается открыть файл User A, включая подделанный путь или ID → отказ до чтения → понятное сообщение → `ACCESS_DENIED` → ничего вне своего корня не прочитано.

**UC-05: сбой БД** → БД недоступна → вход и файловые операции блокируются, UI не аварийно завершается, экран диагностики. Нельзя маркировать операцию завершённой, когда её результат не сохранён/не подтверждён.

## 10. Критерии приёмки и сдача

1. Собирается и запускается на целевой Windows-конфигурации; есть проверенные команды сборки, тестов и миграций.
2. Все FR-01…FR-08 реализованы; основные 6 модулей исходной методички представлены в интерфейсе.
3. Нет неконтролируемого доступа вне пользовательской области; SQLi/Path Traversal/XXE/ZIP Slip/ZIP Bomb/чужой файл проверены негативными тестами.
4. Таблицы Users/Files/Operations физически существуют, связи и ограничения проверены через SSMS.
5. После создания/изменения/удаления/архивирования есть соответствующие успешные и ошибочные записи в аудите.
6. WPF-дизайн соответствует `DESIGN_SPEC.md`, макет используется как ориентир, а не как фон всего окна.
7. `TASKS.md` отражает реально завершённые этапы; каждый завершённый этап содержит результаты сборки/тестов.
8. В `docs/` есть README запуска, схема БД, список тестов и скриншоты для отчёта.
