# AGENTS.md — Постоянные инструкции Codex для Secure File Manager

Этот файл должен находиться **в корне репозитория**. Он определяет правила выполнения задач Codex для WPF-приложения Secure File Manager. Не считать его пользовательским интерфейсом или исходным кодом.

## 1. Обязательный контекст перед любым изменением

1. Прочитай `TECHNICAL_SPEC.md` — требования и безопасность.
2. Прочитай `DESIGN_SPEC.md` и открой `design/egyptian-ui-concept.png` перед работой над UI.
3. Прочитай `TASKS.md`, выбери **только следующий невыполненный этап/задачу**, если пользователь не указал другой объём.
4. Ознакомься с существующим деревом проекта, `.sln`, `csproj`, конфигурацией, тестами, миграциями и изменениями Git. Не перезаписывай чужие изменения.
5. Приоритеты в случае противоречий: безопасность/формальные требования исходного задания → `TECHNICAL_SPEC.md` → `DESIGN_SPEC.md` → `TASKS.md` → детали реализации. Если источники реально противоречат, сообщи пользователю, **не выдумывай согласование**.

## 2. Главная цель

Создать **настольное WPF-приложение** на C#/.NET для защищённого управления файлами с Microsoft SQL Server, EF Core, архитектурой MVVM и мягкой египетской темой. Это **не консольное приложение**. Не заменяй WPF на WinForms, браузер, Electron, MAUI или консоль ради упрощения.

Не внедряй дополнительные возможности (облачную синхронизацию, сетевой API, плагины, автозагрузчики, роли с глобальным доступом) без прямой задачи пользователя.

## 3. Техническая совместимость — до создания проекта

- Проверь установленную **версию Visual Studio**, `dotnet --info`, наличие SDK и `Microsoft SQL Server Engine`. SSMS 19 **не** является сервером.
- Предпочтительный TFM — `net10.0-windows` при наличии **Visual Studio 2026 (18.0+)**. Если установлена только **Visual Studio 2022**, не выбирай .NET 10 в надежде, что IDE его поддержит. Для VS 2022 предварительно проверь поддерживаемые TFM/SDK (например, .NET 9 при VS 17.12+); фиксируй временный выбор и необходимость обновления, поскольку поддержка .NET 8 и 9 заканчивается в ноябре 2026.
- Пакеты EF Core и провайдер должны иметь согласованные основные версии; избегай preview-пакетов без необходимости.
- Если среда недоступна, остановись на точном блокере и дай конкретные шаги установки. **Не утверждай**, что сборка или подключение успешно проверены, если проверки не выполнены.
- Не подменяй локальное подключение к SQL Server «моками» как единственную интеграционную проверку. Моки полезны для unit-тестов, а реальную БД проверяй отдельно.

## 4. Обязательная структура и зависимости

```text
src/SecureFileManager.Wpf/       # Views, ViewModels, XAML, ресурсы, составление DI
src/SecureFileManager.Core/      # Модели, контракты, сервисы, безопасность, результаты
src/SecureFileManager.Data/      # EF Core DbContext, репозитории, миграции, DI данных
tests/SecureFileManager.Tests/   # xUnit
design/egyptian-ui-concept.png   # визуальный ориентир
docs/                         # решения, инструкции, тест-отчёты, скриншоты
```

- Core не ссылается на WPF, EF Core или SQL Server.
- Data ссылается на Core, но не на WPF.
- Wpf ссылается на Core; на Data — только для composition root / DI.
- Views не содержат SQL-запросов, проверок доступа и файловых операций. Бизнес-логика — в сервисах.
- ViewModels взаимодействуют через интерфейсы, `ICommand`, bindable state; code-behind допускается для технического WPF UI-поведения, не для бизнес-операций.
- Не вводи одновременно несколько альтернативных DI-контейнеров, ORM, логгеров или MVVM-фреймворков, если это не обосновано задачей.

## 5. Правила работы с безопасностью (не отключать для «починки»)

1. **Пути:** все операции происходят внутри собственного `Storage/Users/<user-id>/`. Проверяй физическую границу, разрешённые имена, traversal и reparse points/ссылки; не предоставляй прямой путь в любую папку Windows. Просмотр характеристик дисков read-only.
2. **Права:** каждую операцию проверяй в сервисном слое на текущего пользователя и владельца, включая операции по ID и прямому пути. Нельзя полагаться только на скрытые кнопки.
3. **SQL:** EF Core LINQ или параметры; не вставляй пользовательский ввод в SQL-строку через интерполяцию/конкатенацию.
4. **Пароли:** используй KDF с солью и версионируемыми параметрами. Не логируй plaintext, хеши, секреты конфигурации, содержимое файлов.
5. **XML:** запрети DTD/внешние сущности, не выполняй небезопасную десериализацию; **не** используй `BinaryFormatter`.
6. **ZIP:** проверяй записи, пути, symlink, размер, количество, коэффициент сжатия и **реальные записанные байты**; распаковывай во временный защищённый каталог и очищай его при ошибке.
7. **Race conditions:** не ограничивайся `File.Exists` + `File.Open`; учитывай конкурентный доступ, безопасные `FileMode`, временные файлы и повторные проверки. Не обещай защиту от привилегированного локального злоумышленника.
8. **Аудит:** успешные, неудачные и отклонённые события имеют корректный результат, UTC, пользователя при наличии, объект/тип. Если БД недоступна, пользовательские файловые операции запрещены; не заявляй «записано в журнал», когда запись не удалась.
9. **Секреты:** не добавляй логины/пароли сервера, `sa`-пароль, строки подключения с секретами в `.md`, `.json` под Git или в исходный код. Для локального подключения предпочтительна Windows Authentication. Не отключай TLS-проверки молча.
10. **Данные:** не создавай фиктивные рабочие файлы без отдельного seed/demo-режима и отметки. Не удаляй реальную БД или пользовательские файлы при запуске тестов.

## 6. Правила интерфейса

- Используй референс в `design/`, но **не** вставляй скриншот как неподвижный фон с нарисованными кнопками.
- Стиль: современный UI, тёмный navy, песочный/папирусный фон, приглушённая бирюза и золото, лёгкие египетские орнаменты.
- Смысл кнопок и стандартных действий важнее мифологической метафоры. Текст в UI — русский.
- Все кнопки действующие либо явно disabled с указанной причиной; не делай ложных индикаций «Журнал активен», «Защищено», если проверка не выполнена.
- Используй XAML ResourceDictionary и переиспользуемые стили; контролы `DataGrid`, `Button`, `TextBox` доступны клавиатурой. Поддерживай окно 1024×640 DIP и масштаб 150%.
- Не добавляй сторонние шрифты и изображения без разрешения на распространение. Не скрывай ошибки визуальными эффектами.

## 7. Границы действий Codex

- Выполняй только текущую задачу/этап из `TASKS.md` и необходимые связанные исправления; перед существенной переработкой соседних этапов сообщи пользователю.
- Не запускай деструктивные скрипты и миграции `DROP DATABASE`, `EnsureDeleted`, `Remove-Item -Recurse` по пользовательскому хранилищу или смену SQL-учёток без явного разрешения.
- Не отключай проверки безопасности, не снимай авторизацию, не заменяй реальный аудит простым `Console.WriteLine`.
- Не внедряй фоновые задачи/службы или несанкционированные сетевые подключения; проект локальный, без отправки данных внешним сервисам.
- Любые предположения, которые могут изменить поведение, записывай в `docs/DECISIONS.md`; технически несущественные детали выбирай самостоятельно, но обоснуй отклонения.
- Если нужен новый NuGet-пакет, объясни назначение, совместимость с TFM и безопасное использование. Не привязывайся к несуществующим версиям.
- Сохраняй код компилируемым после каждого этапа. Когда из-за исходной среды проверить нельзя, отмечай ограничения, не ставь галочку «готово».

## 8. План работы внутри этапа

1. **Исследовать:** что уже создано, какие требования и тесты относятся к задаче.
2. **Сформулировать минимальную реализацию:** перечислить затронутые классы/файлы, критерии результата.
3. **Реализовать:** не ломать существующую архитектуру; писать тестируемую логику.
4. **Проверить:** сборка, автоматические тесты, затем ручной GUI/SQL Server по доступности.
5. **Сверить:** выполнены ли конкретные acceptance checks и не нарушены ли SEC/NFR.
6. **Зафиксировать:** отметить чекбоксы `TASKS.md` **только** если есть основание, добавить результат и команды в `docs/PROGRESS.md`.
7. **Отчитаться:** кратко объяснить, что сделано, какие файлы изменены, что проверено, что не проверено и что делать дальше.

## 11. Определение «готово» (Definition of Done)

- Указанные функции реализованы без заглушек и отражены в UI или тестах.
- Сборка на целевой среде успешна; связанные тесты прошли (или явно отмечено, что проверки невозможны и почему — тогда этап **не** полностью готов).
- Ключевые ошибки обработаны, пользователь не теряет данные без подтверждения.
- Риски SQL/Path/XXE/ZIP/прав при затрагивании соответствующего модуля покрыты проверками.
- Аудит и метаданные соответствуют файловой системе после операции.
- `TASKS.md` и `docs/PROGRESS.md` обновлены фактически, а не декларативно.
