## Подготовка

2. В VS 2022 открыть SecureFileManager.sln, Debug, профиль SecureFileManager (Development), F5.

   Не менять базу, корень и Windows ACL. Проверять только новую личную папку stage08-check.

## Состояние журнала

В шапке, журнале и настройках используется один источник состояния.

| Действие | Ожидаемый результат |
|---|---|
| Настройки → «Проверить журнал» | Проверяются SELECT и INSERT/constraints/triggers в SQL-транзакции, затем rollback; фиктивная запись не остаётся |
| Проверка успешна | «Журнал: активен», время последнего подтверждения, оговорка о текущей доступности |
| Нет известного результата / прошло более 2 минут без подтверждённых записей | «Не проверен / проверка устарела»; UI обновляет надпись до 15 секунд, SQL фоном не опрашивается |
| Произошла ошибка обязательного аудита | «Недоступен»; обычная успешная запись сообщения об ошибке не скрывает известный сбой; повторная явная проверка может подтвердить восстановление |

Нельзя безопасно отключать рабочий SQL во время операций с ценными данными. Для воспроизводимого
отказа использовать `./scripts/Test-Stage08.ps1 -Filter 'FullyQualifiedName~AuditProbeRollsBack|FullyQualifiedName~RealAuditFailure|FullyQualifiedName~JournalAndDiagnosticsMissingDatabase'`.
Скрипт работает с собственной новой GUID-БД и каталогом; тестовый trigger ставится только в ней
и снимается finally. Проверяются ошибка, статус, fail-closed, rollback и успешный повтор.
Интерактивный сценарий outage допустим только на отдельно настроенной копии приложения с тестовыми
учётными записями, отдельной БД/StorageRoot и без незавершённых операций; не останавливать общий Engine.
Возвратить доступ к той же тестовой БД, нажать «Проверить журнал» и «Обновить»; успех только по факту.

## Неразрушающая диагностика

Настройки → «Проверить хранилище без исправлений». До 10000 физических объектов/записей;
при недоступности или превышении лимита отчёт явно неполный. Исправления не выполняются.

| Проверка только в stage08-check | Ожидаемый результат |
|---|---|
| Создать безвредный новый файл через Блокнот в своей тестовой папке | UNTRACKED, автоматически не присвоен; после осознанного «Сверить» можно учесть |
| Изменить известный тестовый файл снаружи | METADATA_CHANGED при изменении размера/времени; старый редактор не перезапишет его молча |
| Убрать только специально созданную ненужную копию снаружи | MISSING; диагностика сохраняет запись Files. Решение о сверке/soft-delete принимается отдельно |
| Soft-deleted путь снова появился снаружи | DELETED_PRESENT, файл не удаляется. Если имя законно создано заново в приложении, это не ошибка старого soft-delete |
| Остались план/backup/staging после сбоя | PENDING_OPERATION и наличие/отсутствие подтверждения SQL; неизвестное/повреждённое — INCOMPLETE_STAGING |
| История и Files не согласуются | AUDIT_METADATA_MISMATCH; требуется анализ, история не удаляется |

Не создавать повреждённые планы вручную в рабочем хранилище. Эти случаи воспроизводит
`DiagnosisFindsPendingAndUnknownStagingWithoutCleaningIt` на временных данных.
Ничего автоматически не чистить. Не удалять .sfm-internal. Прежнее «Восстановить» применимо
только к проверяемому собственному плану и тем же SQL/Storage; при внешней подмене остановиться
и сохранить резервные копии для ручного разбора. Содержимое одинакового размера/mtime без baseline
диагностика не сравнивает: для редактора работает отдельный fingerprint/SHA-256/RowVersion.

## SQL: только SELECT

Подставить GUID своего пользователя. Не выбирать PasswordHash, содержимое или секреты конфигурации.
Доступ SSMS под Windows — отдельные права; ограничения приложения не защищают от SQL-администратора.

```sql
DECLARE @Owner uniqueidentifier = '00000000-0000-0000-0000-000000000000';
SELECT Id, Username, IsActive, CreatedAtUtc FROM Users WHERE Id = @Owner;
SELECT TOP (100) Id, Name, RelativePath, SizeBytes, ModifiedAtUtc, IsDeleted, DeletedAtUtc
FROM Files WHERE OwnerId = @Owner ORDER BY ModifiedAtUtc DESC;
SELECT TOP (100) Id, OccurredAtUtc, OperationType, Result, FileId, TargetPathSnapshot, Details, CorrelationId
FROM Operations WHERE UserId = @Owner ORDER BY OccurredAtUtc DESC, Id DESC;
SELECT OperationType, Result, COUNT_BIG(*) AS EventCount
FROM Operations WHERE UserId = @Owner GROUP BY OperationType, Result;
```
