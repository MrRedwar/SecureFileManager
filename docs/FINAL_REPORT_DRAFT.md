# Secure File Manager — основа учебного отчёта

Черновик от 03.11.2026, C#-версия HEAD 598b175. Персональные реквизиты, требования
оформления учебного заведения и настоящие иллюстрации добавляет автор.
Статус результатов — TEST_REPORT; эта работа не является завершённой ручной приёмкой.

## Введение

Управление файлами сочетает операции с диском, пользовательский ввод и ведение истории.
Ошибки проверки путей, владения или структуры архива могут привести к выходу за рабочую
область и потере данных. Поэтому учебный файловый менеджер полезен как практическое
объединение настольного интерфейса, реляционной модели и проверяемых защитных механизмов.

Цель проекта — создать Windows-приложение Secure File Manager для работы с личными
файлами, TXT/JSON/XML и ZIP с аутентификацией, контролем доступа и журналом операций.
Задачи: определить границы хранения, реализовать WPF/MVVM, модель SQL Server,
согласование файловых операций и метаданных, ограниченные парсеры и негативные тесты,
подготовить воспроизводимую сборку и демонстрацию.

## 1. Постановка задачи

Приложение работает локально, без внешнего прикладного API и облачной синхронизации.
Пользователю доступны регистрация/вход, сведения о дисках, собственные файлы и папки,
импорт копированием, текстовые редакторы, ZIP и собственный журнал.
Каждый файл связан с владельцем, путь ограничен личным GUID-каталогом.
Отказы не должны создавать ложный успех, а невалидный документ — портить прежние байты.
Основные формальные источники: TECHNICAL_SPEC, DESIGN_SPEC, TASKS.

Требования безопасности включают SQL-параметризацию, path/owner проверки в сервисах,
KDF с солью, запрет DTD/XXE, ZIP Slip/Bomb limits, устойчивое согласование SQL/FS и
правдивый аудит. Допустимость WPF и Microsoft SQL Server по методичке остаётся отдельным
вопросом согласования с преподавателем (PRE-03); наличие согласования здесь не утверждается.

## 3. Архитектура приложения

Решение состоит из Core, Data, Wpf и Tests. Core хранит модели и контракты, выполняет
авторизацию и оркестрацию файловых операций, не зависит от EF/WPF. Data реализует SQL
mapping, миграции и транзакционные адаптеры. Wpf содержит представления, ViewModels,
ресурсы и Windows-specific IO; DI находится в App. Бизнес-операции вызываются через
интерфейсы сервисов, а не выполняются обработчиками кнопок.

Модель содержит Users, Files и Operations. Ключи GUID, FK NO ACTION; Files включает
File/Directory, owner/path, даты, размер, soft-delete и RowVersion. Operations хранит
nullable actor/file, UTC, тип/результат, безопасные snapshots и correlation.
Уникальность логина и активного owner/path закреплена индексами SQL.
Две миграции: InitialCreate и AddLoginFailureWindow. Полная схема/диаграмма и ограничения
приведены в ARCHITECTURE, без упрощения фактической модели.

Байты хранятся в настраиваемом StorageRoot/Users/<GUID>, SQL содержит только метаданные.
Служебный .sfm-internal хранит staging и планы восстановления; пользователь не выбирает
произвольный OS-путь назначения. Для изменяющих действий используется общий протокол
prepare → publish → Files+audit commit → settle с компенсацией и проверкой ambiguous commit.

## 4. Реализация функциональности

Регистрация проверяет логин/пароль/подтверждение, готовит GUID-каталог и атомарно
фиксирует User с обязательным аудитом. Вход проверяет версионированный hash, счётчики
ошибок и активность; сессия начинается после commit. Выход очищает чувствительное состояние.

«Диски» показывает реальные DriveInfo read-only сведения. «Мои файлы» объединяет
физический список и owner-scoped SQL; поддерживает создание, чтение, сохранение,
подтверждаемое удаление, поиск/сортировку и явную сверку. Непустые папки не удаляются
рекурсивно. Импортирует один выбранный локальный файл до 100 МиБ, не меняя источник.

Общий редактор работает с UTF-8 до 10 МиБ, dirty-state, Ctrl+S, подтверждением закрытия,
конфликтами и явным перечитыванием. JSON/XML проверяются в сервисе до Save; раздел
«JSON / XML» использует тот же FileService и координатор окон, без отдельной копии документа.

ZIP создаётся из выбранных личных объектов (Store), preview показывает структуру,
распаковка Store/Deflate публикует только новое дерево. Превышение лимитов, опасная
структура или конфликт не приводят к пофайловому слиянию с существующими данными.
Журнал предоставляет свои события, серверные фильтры/сортировку/страницы и безопасные
описания; настройки показывают фактическое состояние аудита и диагностику расхождений.

## 5. Реализация безопасности

Контроль доступа повторяется в сервисном слое: current session/revision, active SQL User,
actor==owner, owner-scoped ID/path, физические handles. EF LINQ и параметризованные SQL
locks не вставляют пользовательский ввод в структуру запроса. PasswordHasher IdentityV3
использует PBKDF2 со случайной солью и cost 600000; одинаковые пароли не дают одинаковых
хешей. Ошибки входа не раскрывают существование пользователя, действует lockout 5/15 минут.

Относительные пути, конечные Windows handles, reparse/hardlink проверки и удержание
предков ограничивают обход каталога. CreateNew, staging, SHA-256 и RowVersion обнаруживают
конкурентные изменения. XML запрещает DTD и resolver, ограничивает сложность; JSON
разбирается в JsonDocument, без активации произвольных типов.

ZIP проверяет пути/коллизии/ссылки, заголовки, CRC, число записей, заявленные и фактические
потоковые байты. Лимиты: 250, 25 МиБ на entry, 100 МиБ total, ratio 100:1.
При ошибке не публикуется частичный конечный результат. Metadata/audit имеют общую SQL
транзакцию; неизвестный исход требует восстановления, а не удаления неизвестных файлов.
Неудачная запись аудита не выдаётся за подтверждённую. Статус аудита учитывает probe
SELECT+INSERT+rollback и реальные commits, а также устаревание подтверждения.

Модель не защищает от Windows/SQL administrator, владельца процесса и прямого доступа
к Storage/БД под тем же Windows token. Нет at-rest encryption, криптографической цепочки
журнала и распределённой SQL+NTFS атомарности. Данные обещания не входят в результат проекта.

## 6. Тестирование

Использованы unit/parser/config/VM проверки, реальный SQL Express, изолированный Windows
FS и WPF STA/layout. Матрица T01–T20 сопоставлена с существующими методами в TEST_REPORT;
инвентаризация каждого test case и источника находится в TEST_INVENTORY.
Рабочая SecureFileManagerDB/Storage не являются целью автоматических тестов.

03.11.2026 выполнен полный Debug-прогон: **160 passed, 0 failed, 0 skipped**;
78 SQL integration и 82 прочих test cases. Длительность VSTest 35 с, TRX-интервал 37.428 с.
Debug/Release сборки успешны без warnings/errors, framework-dependent publish успешен.
EF подтвердил отсутствие model changes после миграции. Запуск опубликованного exe
из TEMP обнаружил окно входа; захват содержимого блокирован timeout helper.

Негативные тесты проверяют SQLi, traversal/чужие ID, junction/hardlinks, XXE/local/loopback,
ZIP Slip/Bomb/CRC, контролируемые SQL/IO/disk-full failures, stale saves, concurrent creation,
ambiguous commit/recovery. Физический disk-full/power loss и отдельная physical file symlink
не проводились. WPF layout/bitmap150 не заменяет native Windows DPI и ввод клавиатурой.

Новых дефектов приложения текущий прогон не выявил, код не исправлялся.
Ранее исправлялись BOM, stale editor version/duplicate windows и failure audit (этап 06),
Windows handles/extended paths (07), SQL collation и описание журнала (08).
Эти сведения подтверждены соответствующими историческими отчётами, не являются числом
вновь найденных уязвимостей. Предварительные ошибки restore/artifacts path были ошибками
окружения/команды, устранены повтором корректной проверки.

GUI/SSMS снимки, чистая установка и формальное согласование выбранного стека.
