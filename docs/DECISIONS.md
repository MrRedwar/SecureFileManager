при отказах. Pending11.03 блокирует внешний редактор, editor-pending11.02 блокирует

не обещаются. Нет новых пакетов/фреймворков, изменения StorageRoot/рабочих данных/коммитов.

## 2026-11-07 — Общее внешнее пространство по прямому поручению пользователя

Пользователь попросил расширить программу до полноценного файлового менеджера и уточнил:

Реализация по этапам 11.01–11.04. В 11.01 вводится read-only IComputerBrowseService и
WindowsComputerDirectoryReader, размещённые во вкладке прежнего раздела «Диски».

существующий IFileService и его owner policy не ослабляются. Внешние объекты не включаются
в личную Files и не усваиваются первым просмотревшим пользователем. Схема SQL не меняется.
Расположения/grants пока не нужны для общей read-only видимости; перед мутациями нужна
отдельная модель общей идентичности/путей и её проверка на тестовой БД.

Общий просмотр ограничен локальными дисками, не следует reparse/junction и не разрешает
UNC/network/device/ADS или dot segments. Перечисление не рекурсивное, до10000 объектов;
ошибки/усечение явные. Session/Revision и active SQL User проверяются до IO, success-аудит
фиксируется до выдачи списка, поздний результат другого пользователя не выдаётся.
Operations: FILE_READ/COMPUTER_DIRECTORY_LISTED, actor/UTC, FileId/TargetPathSnapshot NULL:
это просмотр каталога без чтения содержимого, абсолютные пути в старый personal snapshot
не вставляются. Полный external path audit для мутаций — часть11.02. Нет background scan,
изменения ACL/поднятия прав, миграций рабочей БД, переноса файлов или auto-seed.

## Этап 07 — ZIP поверх общего файлового протокола, 02.11.2026

Восстановлен фактический контекст HEAD 2410ae0. Этап 06 принят пользователем;
прежняя фраза об открытой ручной приёмке выше описывает снимок до его подтверждения.
Незавершённых функций 06, блокирующих ZIP, не найдено. Специальные native/DPI/power-loss
ограничения не выдаются за подтверждённые общим сообщением пользователя.

IArchiveService — узкий ZIP-фасад **того же singleton FileService**, не второй CRUD/оркестратор.
Переиспользуются Run/gate/session/revision/access, SQL active User/owner lock,
FileTransactionStore, Files/Operations, Stage/Publish/Settle/recovery. Схема/миграции/корень
и направление Core→без WPF/SQL сохранены. System.IO.Compression входит в .NET, новых пакетов нет.

Распаковка выполняется только в новую именованную папку внутри выбранного разрешённого
родителя. Слияния с существующими папками и overwrite нет. Такая форма публикует всё дерево
одним handle-bound rename, а не набором независимых переносов. Пользователь явно выбирает
родителя и новое имя, видит предварительный просмотр и подтверждает извлечение.

IFileWorkspace расширен OpenBinary и StageGenerated; доверенный callback получает только
IFilePreparation с проверяемыми относительными именами. Данные записываются CreateNew
в прежнюю private .sfm-internal/<transaction>/new. Подготовленные файлы Flush(true).
FileJournal.Kind дополнен Archive/Extract без изменения чисел прежних enum-значений.
Для Extract добавлен Tree: относительный путь, вид и SHA-256+identity/mtime/size файла
либо identity каталога. Plan ограничен 1 МиБ, дерево <=250 узлов, прежние планы совместимы.
Проверяются также синтезированные родительские папки: суммарно не более 250 выходных узлов.

После публикации все новые Files и ZIP_EXTRACTED/FILE_TX_ZIP_EXTRACTED фиксируются прежней
SQL-транзакцией. При rollback снимается только совпадающее с планом дерево, после проверки
всего состава и удержания handles; чужие/внешне изменённые данные не удаляются.
Неопределённый commit проверяется прежним FILE_TX_* CorrelationId. Пока БД недоступна,
артефакты сохраняются, обычные операции блокируются. Восстановление завершает committed
дерево либо удаляет только неизменённое uncommitted дерево. Поломанный/неполный plan
требует ручного разбора. SQL и NTFS не образуют распределённой атомарной транзакции.

ZipEngine работает только с потоками: предварительная проверка EOCD/central/local headers
до выделения ZipArchive entries, затем ZipArchive/ZipArchiveEntry. Поддержаны Store/Deflate,
data descriptor; ZIP64, многотомные, зашифрованные и прочие методы явно отклоняются.
Архив ограничен 101 МиБ, central directory — 1 МиБ, записей — 250.
Пути ZIP: только `/`, без backslash/mixed separators, абсолютных/UNC/дисковых путей,
traversal/ADS/резервных имён/опасных окончаний/служебного .sfm-. Сохраняется лимит Files-пути
400 и имени 255, включая итоговый путь под новой папкой. Дубли/предки-файлы проверяются
OrdinalIgnoreCase; несовпадения SQL collation при позднем insert компенсируются транзакцией.
Unix symlink/device/special modes и DOS reparse/device-флаги отвергаются; атрибуты/ACL из ZIP
не восстанавливаются. Физические предки pin-ятся, handles проверяются, ссылки не следуются.

ZipLimits immutable и внедряем через конструктор FileService; можно только ужесточать
дефолты 250 / 25 МиБ / 100 МиБ / 100:1. Runtime UI-настроек лимитов нет.
Проверяются заголовки, заявленные размеры, фактические per-entry/total байты и ratio перед
каждой записью блока (64 КиБ), совпадение фактической длины и CRC32. В память не загружается
весь ZIP или содержимое записи. Preview не распаковывает/не проверяет содержимое потоком:
размеры и возможность извлечения предварительны; CRC/реальные байты — на Extract.

Создание ZIP использует Store/NoCompression: даже повторяющиеся исходники не создают ZIP,
нарушающий собственный anti-bomb ratio. Сжатие не предлагается как отдельная настройка.
Источники — owner-scoped FileId, вложенные объекты повторно сопоставляются с Files/ФС;
неучтённые/пропавшие/изменённые дети требуют явной сверки. Пересекающийся выбор дедуплицируется,
коллизии entry names отвергаются, destination внутри исходной папки запрещён.
ZIP_CREATED/ZIP_EXTRACTED и safe failure codes идут в прежние Operations, без имён записей/содержимого/сырого исключения в Details.

Обнаруженные Windows-детали исправлены минимально: Pin переиспользует уже проверенный
exclusive directory handle; перед tree settle собственные read-only pins заменяются handles
проверяемого дерева. SafeNativeFile использует extended local paths для глубокого staging;
физическая граница проверяется по final handle path, не строковому StartsWith(root).
OpenBinary явно перематывает поток после fingerprint и Create проверяет полную длину копии.

WPF использует прежний FilesView/VM: Extended selection, существующая «Архивировать»,
предпросмотр/распаковка/отмена. Одиночные действия выключены при множественном выборе.
В Archives переиспользованы фильтр ZIP+каталоги и вкладка выбора источников; контент документа
редактора не дублируется. Новые диалоги — тематические WPF, только личный browser назначения.
Сессия очищает выбор/браузеры, закрывает ZIP-диалоги, отменяет подготовку; запоздалый progress
не превращает отказ или новый сеанс в Success. Отмена не уничтожает уже committed результат.

140 тестов прошли, но native GUI/keyboard/DPI/оконные подтверждения остаются ручной приёмкой.
Нет гарантий против привилегированного/того же Windows token с прямым доступом к диску/SQL,
любого power loss/контроллера. Реальный full disk и отдельная file symlink не воспроизводились;
есть контролируемые IO/SQL faults, реальная junction/hard link и reparse-политика.

## Этап 08 — журнал и диагностическая сверка, 03.11.2026

Схема/enum/миграции не меняются. IJournalService получает пользователя только из IUserSession,
проверяет SQL active User и Revision после awaits. OperationRepository.QueryAsync выполняет
owner/type/result/UTC date/search predicates, whitelist bool sort и Skip/Take на SQL Server.
До 100 строк по контракту, UI 50; максимум 10001 страниц. HasMore определяется extra-row,
не полной загрузкой Operations. Системные UserId=NULL остаются вне пользовательского UI.
Дата «по» включительна в локальном календаре, SQL получает исключительную UTC-границу.
Динамический SQL не вводится. Сортировка отдельных колонок DataGrid отключена, чтобы
локальная сортировка страницы не притворялась сортировкой всей истории.

Журнал не выводит исходные Details. JournalService пропускает только известные безопасные
коды для локализованных описаний, остальное скрывает, не меняя исходную Operations.
Подозрительный несуществующий логин с символами вне letters/digits/._- не сохраняется
в ActorNameSnapshot; остаётся nullable системное LOGIN_FAILED. Для существующего пользователя
сохраняется его подтверждённое имя. Блокировка уже работала; LOGIN_LOCKED уточняет её событие
в прежнем LOGIN_FAILED. KDF, формат паролей и параметры production не меняются.

IAuditHealth — общий singleton; probe SELECT+реальная INSERT внутри rollback-транзакции
проверяет права/constraints/triggers и не оставляет synthetic audit row. Реальные транзакции
и SecurityAudit дают commit/error feedback. Ошибка latched до новой успешной полной пробы,
старый probe не перекрывает более свежую ошибку. Active устаревает через 2 мин; UI timer15 с
только перечитывает snapshot, нет фонового SQL polling/службы. Это не гарантия будущего commit.

IStorageDiagnostics реализуется тем же FileService/Run/workspace/owner transaction. Диагностика
не исправляет Files/пользовательские данные/историю, только создаёт собственный FILE_READ audit.
До 10000 физических объектов и записей (10001 для обнаружения превышения), отчет явно неполный
при ошибках/усечении. Включены soft-delete, untracked/missing/type-size-mtime mismatch, audit
mutation relationship (включая потомков ZIP_EXTRACTED) и pending plans/SQL success correlation.
При разных collation Files и Operations сравнение snapshot явно COLLATE Latin1_General_100_CI_AS,
без миграции. Unknown internal files теперь блокируют обычные операции вместо игнорирования.
Автоматического удаления/присвоения/подчистки нет. Старая явная Synchronize/Recover сохранена.

Сверка без stored hash baseline не определяет изменение байтов с тем же size/mtime и не
доказывает историческую целостность БД. Snapshot может устареть; перед каждым изменением
сохраняются собственные session/owner/path/handle/version checks. SQL и NTFS — разные ресурсы.
Новый контроль не обещает защиту от того же Windows token/администратора с прямым SQL/диском.
Подробности: STAGE08_SECURITY_AUDIT.md и STAGE08_MANUAL_TEST.md. Этап 09 не начинается.

Файловая транзакция подтверждает health только если ObservedAudit прежнего OperationRepository
выполнил Add и commit подтверждён. Пустой Recover/SQL work не доказывает возможность INSERT
в Operations и не переключает Unknown в Active. Это закреплено отдельным SQL-тестом.
