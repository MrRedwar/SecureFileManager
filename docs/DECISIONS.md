## 2026-11-01 — Этап 03.5: расширяемая архитектура хранения

Решение: ближайшие этапы реализуют только A (Personal Secure Storage). Возможный B
(Authorized Windows File System Access) — отдельно согласуемое расширение, не включённый
режим и не разрешение доступа ко всем дискам. Импорт из Windows — будущая копия файла
в A, не способ зарегистрировать внешний корень и не скрытая реализация B.

Проверены реальные Core/Entities/Interfaces, Data/AppDbContext/Repositories/DI,
csproj, WPF composition root/VM и тесты. Core не зависит от EF/WPF/SQL, Data не зависит
от WPF. В коде пока только три репозиторных интерфейса; файловых/auth/session/policy
сервисов нет. Поэтому срочных исправлений кода/контрактов перед этапом 04 не требуется.
Новые абстракции, .cs-файлы, проекты, пакеты и миграции не добавляются.

Будущие Authentication и Session отделены от физического корня и решения о доступе.
IFileService/IPathPolicy/IAuditService из ТЗ вводятся при реализации потребителей.
IFileAccessPolicy обоснован для 04.05 (ownership/action), но не создаётся пустым сейчас.
IStorageProvider избыточен для двух режимов одного локального IO. IStorageLocationPolicy
понадобится только при реальном каталоге нескольких разрешённых расположений/grants;
для A достаточно доверенного резолвера личного корня и IPathPolicy.

Выявлены ограничения расширения: unique (OwnerId,RelativePath) без LocationId;
синтаксический MetadataPath не проверяет физическую границу/ACL; audit AddAsync требует
совпадения актора и владельца FileId; отдельные DbContext репозиториев не образуют
общую SQL-транзакцию; singleton VM требуют очистки при смене сессии. IFileRepository
сам не аутентифицирует переданный ownerId. IUserRepository потребуется дополнить
атомарным обновлением lockout в этапе 04. Это план будущей реализации, не основание
выдавать текущую заготовку за готовую авторизацию или ослаблять её проверки.

Для нескольких корней документированы будущие StorageLocations/Files.LocationId,
индекс активного пути с расположением, различия личного/общего каталога, grants,
идентичность актора и безопасные location snapshots в аудите. Только новые миграции
после отдельного решения B; InitialCreate не меняется. Старые Id, soft-delete и история
сохраняются, физические файлы не перемещаются автоматически. Нельзя просто убрать
owner-проверки в существующих репозиториях или записывать абсолютный путь в RelativePath.

Текущие TECHNICAL_SPEC/AGENTS ограничивают файловые действия личным корнем. B расширит
эту границу, импорт потребует узкого read-only исключения для выбранного источника.
Это различие явно зафиксировано: перед реализацией нужны обоснованные уточнения FR/SEC,
сейчас действующие ограничения сохраняются. TECHNICAL_SPEC.md не изменён.

Подробности, модель разрешений Windows, риски и последовательность миграции —
docs/STORAGE_ARCHITECTURE.md. Вход приложения не создаёт Windows security token;
ACL процесса не подменяет изоляцию пользователей приложения. Переписывать проверку
пароля для B не потребуется при сохранении разделения identity/session/access policy,
но модели расположений, репозиториям и аудиту понадобятся целевые расширения.

В TASKS.md добавлен завершённый блок 03.5 и запланированная 05.10 (импорт), все задачи
04/05 остаются невыполненными. Готовность: можно приступать к этапу 04 для A после
разрешения пользователя; поддержка B не объявляется реализованной.


## 2026-11-01 — Этап 04: Identity, сессии и граница личного хранилища

Разрешён пользователем только этап 04, режим A. Новый пакет Core —
Microsoft.Extensions.Identity.Core 9.0.22: штатный IdentityV3 PasswordHasher PBKDF2/
HMAC-SHA512, соль, 600000 итераций, versioned hash/rehash при успешном входе.
Core остаётся без EF/WPF/SQL. Пароль передаётся из PasswordBox кратковременно,
не становится bindable-свойством VM или частью сессии. Managed string не гарантирует
обнуление памяти; это ограничение явно не выдаётся за SecureString-изоляцию.

UserSession хранит только Id/Username/Revision. Authentication/Session не знают Storage.
Registration вызывает доверенный IPersonalStorageProvisioner, рабочая область —
IUserStorageService с IUserSession/IFileAccessPolicy/IPathPolicy. Физический адаптер
PersonalStorage находится в Wpf/Infrastructure/FileSystem, не в Views/VM:
SQL-слой Data сохраняет свою ответственность. IStorageProvider/location catalog/режим B
не вводятся. Корень по умолчанию LocalApplicationData/SecureFileManager/Storage,
переопределение SFM_STORAGE_ROOT — абсолютный локальный путь. Релокатор не реализован.

LoginProtectionPolicy параметризует 5/15/15; IClock — UTC. В новой миграции
20261101122237_AddLoginFailureWindow добавлен только nullable FailedLoginWindowStartUtc.
Скользящее окно уточняется последними counted LOGIN_FAILED в Operations; после
успеха/истечения блокировки старый набор ошибок не учитывается. Существующие миграции,
уникальность логинов/Files.RelativePath и FK не меняются.

Нужна общая SQL-транзакция User-состояния и обязательного аудита. Минимальный
IIdentityStore/IIdentityTransaction реализован в Data через Serializable/UPDLOCK/HOLDLOCK;
существующий OperationRepository подключается к той же транзакции/connection.
Повторяется только SQL deadlock 1205, максимум три попытки, с тем же GUID каталога.
Неопределённый commit автоматически не повторяется. Общую транзакцию файловых
метаданных/аудита этапа 05 этот узкий identity-порт не подменяет.

При регистрации insert User не коммитится до успешного mkdir и аудита.
При отказе rollback не удаляет каталог/существующие файлы. Возможны пустые orphan GUID
и неопределённый commit: сначала проверяют вход, затем повтор регистрации;
для committed User каталог может быть безопасно подготовлен при входе. Автоматического
удаления сирот нет. Пустой каталог после SQL-отката сам по себе не создаёт аккаунт/доступ.

При недоступном SQL или невозможном обязательном аудите входа/регистрации успеха нет.
Logout всегда завершает сессию, даже если LOGOUT не удалось записать; UI сообщает,
что журнал не подтверждён. Безобъектные события имеют NULL FileId/TargetPathSnapshot,
неизвестный логин — NULL UserId и безопасный валидный ActorNameSnapshot. Пароли/хеши
в Operations отсутствуют; обычному пользователю глобальные unknown-события не выдаются.

Политика личного пространства проверяет текущую сессию, владельца, активность/SQL,
Revision после await, нормализованные сегменты/границу, reparse chain и hard links.
Не меняются ACL директорий. Наследуемые ACL и один Windows token не дают полной
изоляции пользователей приложения от прямого доступа тем же Windows-пользователем.
Проверки пути не устраняют все TOCTOU: конечные handle, безопасные FileMode/temp и
согласованность мутаций — обязательная работа этапа 05. Полноценного CRUD сейчас нет.

Главное окно/тема сохранены; вход/регистрация — отдельное окно с прежними ресурсами.
При смене Session singleton VM сбрасывают пользовательское состояние и навигацию,
окно создаётся заново. Стартовая проверка SQL даёт только диагноз подключения,
разрешение входа всегда требует пароля, активности/lockout и commit аудита.

Подробности, проверенные сценарии и ручные ограничения — STAGE04_REPORT.md.

## 2026-11-02 — Профиль локальной разработки для VS 2022 / SDK 9

Причина отказа SQL-подключения при запуске из VS: без профиля SFM_ENVIRONMENT не задан,
используется Production с обязательной проверкой сертификата, а игнорируемый
appsettings.Development.json из каталога проекта не читается. SQL Engine/база/миграции
доступны; локальный SQL Express выдаёт недоверенный сертификат.

В Wpf/Properties/launchSettings.json добавлен SecureFileManager (Development):
SFM_ENVIRONMENT=Development, SFM_CONFIG_DIRECTORY=., workingDirectory=$(ProjectDir).
Для SDK 9 CLI рабочий каталог также задаётся RunWorkingDirectory=$(MSBuildProjectDirectory)
в csproj: Visual Studio раскрывает ProjectDir в профиле, CLI использует свойство MSBuild.
Нет абсолютной привязки к компьютеру, строки подключения или секретов в профиле.
Источник настроек — существующий игнорируемый локальный файл, не bin/publish.

Production по умолчанию и DatabaseConfiguration.Validate не изменены. Прямой запуск
exe/--no-launch-profile не включает Development. TLS остаётся обязательным; локальное
TrustServerCertificate=True допускается прежней политикой только в Development.
Это исправление запуска этапа 04, не начало этапа 05.

Поведение профилей и рабочих каталогов сверено с документацией SDK
[dotnet run](https://github.com/dotnet/docs/blob/main/docs/core/tools/dotnet-run.md)
и установленным Microsoft.NET.Sdk.targets SDK 9.0.200; фактический dotnet run
с новым профилем без предварительных SFM-переменных подтвердил подключение в WPF.


## 2026-11-02 — StorageRoot в существующем JSON, без AppData fallback

По поручению пользователя, уже самостоятельно перенёсшего Storage на D:, корень теперь
явно конфигурируется параметром StorageRoot в существующем локальном Development JSON.
Никакого второго переноса или изменения SQL GUID не выполняется. Проверенная структура
Storage/Users/{GUID} совпадает с существующим активным пользователем SQL Server.

Использованы прежние SFM_ENVIRONMENT/SFM_CONFIG_DIRECTORY и имена appsettings.
Совместимость SFM_STORAGE_ROOT сохранена: непустая переменная имеет приоритет,
пустая считается незаданной, как у SQL override. Отдельная система настроек/пакет
конфигурации не добавляется. Отсутствие валидного StorageRoot теперь останавливает
подготовку приложения; неявный корень в AppData удалён. У альтернативного недоступного
диска нет fallback, возвращается StorageStatus.Unavailable и прежняя безопасная ошибка.

Production не получает локальный путь. Прямой exe запускается с явно заданным
окружением/каталогом конфигурации, профиль VS не считается свойством собранного бинарника.
Для новой установки пустой StorageRoot в example-файле нужно заполнить явно.

По запрету создания новой БД SQL fixture дополнена явным повторным использованием
SFM_EXISTING_TEST_DATABASE только с шаблоном SecureFileManagerTests_<32 hex>.
Несуществующая БД/неактуальная схема отклоняются без создания/миграции. Два старых теста
метаданных теперь ограничивают выборки собственными UserId/Id вместо предположения
пустой БД; данные других тестов не удаляются. SFM_STORAGE_TEST_ROOT размещает только
изолированные test-only каталоги на D:, вне рабочего Storage.

При повторном прогоне выявлена независимая нестабильность скрытого native WPF-окна:
WM_SIZE сохранял предыдущие размеры, затем desktop pump зависал. WpfShellTests
проверяет логический клиентский layout без Window.Show/desktop pump, сохраняя проверки
размеров, ресурсов, привязок и видимости состояний через их Visibility. XAML приложения
не меняется; реальный native resize/DPI не выдаётся за автоматически проверенный.

Итог: restore/build успешны, 47/47 тестов без пропусков; read-only проверка собранного
адаптера загрузила локальный StorageRoot и нашла прежний GUID-каталог.
Инструкция — STORAGE_CONFIGURATION.md. Этап 05 не начинается, коммит не создаётся.
