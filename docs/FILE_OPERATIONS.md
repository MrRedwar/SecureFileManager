# Файловые операции и согласованность SQL/NTFS — этап 05

Дата: 02.11.2026. Только Personal Secure Storage (A).

## Слои

- Core/Files: IFileService, FileService, DTO/результаты/лимиты, IFileTransactionStore,
  IFileWork, IPhysicalFileStorage/IFileWorkspace. Core не зависит от WPF/EF/SQL Server.
- Data/Files/FileTransactionStore: serializable-транзакция, проверка активного User
  с UPDLOCK/HOLDLOCK, прежние FileRepository/OperationRepository на общей connection/
  transaction. Повтор SQL callback автоматически не выполняется.
- Wpf/Infrastructure/FileSystem: локальный Windows-адаптер, private staging, Win32 handles.
  Wpf/Infrastructure/Dialogs: только UI-выбор/подтверждения. VM не читает/пишет диск.
- App.CreateServices — единый composition root для запуска и проверки DI.
  Files/Drives активируются после входа и при выборе раздела. Editor получает IFileService.
  Changed уведомляет UI только после подтверждённого commit и завершения staging.

Схема БД не менялась. Files.RelativePath, OwnerId, soft-delete/RowVersion и Operations
сохранили прежние ограничения. ListChildrenAsync ограничивает запрос SQL текущей папкой
и 10001 записью для обнаружения лимита, не загружает все файлы пользователя в UI.

## Граница доступа

В каждом прикладном вызове: текущая Session/Revision, User.IsActive в реальной SQL,
actor == owner, owner-scoped FileId и проверенный относительный путь. Root не является
файловой записью, удалить его через FileService нельзя. Ревизия сессии проверяется
перед публикацией и аудитом; уже начатое действие не получает права нового пользователя.
Приложение перед выходом закрывает/сохраняет редакторы и ждёт завершения файловой команды.
Смена Session очищает редактор/списки/поиск/выбор, запоздалые результаты VM отбрасывает.

Имена Windows/зарезервированные устройства (включая CONIN$/CONOUT$ и COM¹/LPT²),
dot/dotdot, ADS, абсолютные пути, длины, служебный префикс .sfm- запрещены.
Пользователь не выбирает физический root в интерфейсе. Root загружается прежним
StorageConfiguration: локально D:/SecureFileManagerData/Storage; fallback отсутствует.

## Handle-проверки Windows

Адаптер открывает объекты с OPEN_REPARSE_POINT и проверяет атрибуты, число hard links,
итоговый путь по handle. Каталоги-родители удерживаются дескрипторами с LIST_DIRECTORY,
без FILE_SHARE_DELETE: attributes-only handles недостаточны для запрета rename.
Открытый источник/редактируемый файл не допускает конкурентную запись; перемещение/
удаление выполняется через проверенный handle, без ReplaceIfExists. После rename
проверяется конечный путь. Буфер FILE_RENAME_INFO завершается NUL.

Поведение share/flags и handle-операций соответствует документации
[CreateFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew),
[FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info)
и [SetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle).
Проверки не дают изоляцию от администратора/того же Windows-пользователя с прямым доступом
к диску и БД. ACL не изменяются, impersonation/обход прав не применяется.

## Протокол изменения

В пользовательском корне служебная скрытая .sfm-internal содержит marker owner, lock
и отдельные GUID-каталоги операций. Внешние команды не могут обращаться к этому префиксу.
Обычные данные с таким именем автоматически не усваиваются и не удаляются.

1. Открыть SQL-транзакцию/проверить User. Захватить межпроцессный lock личного хранилища,
   проверить отсутствие pending-журналов. Проверить имя/конфликт/метаданные/версию.
2. Подготовить новый файл с CreateNew либо пустую папку в private transaction directory.
   Импорт копируется по 64 КиБ; лимит контролируется по реально записанным байтам.
   Данные и JSON plan сбрасываются Flush(true) до изменения пользовательского имени.
3. Для Save/Delete исходный объект по проверенному handle перемещается в old;
   для Create/Save/Import/Directory подготовленный new публикуется без перезаписи.
   Исходная версия/identity и после-версия записаны в плане.
4. В той же SQL-транзакции сохранить Files/RowVersion и обязательный Operations.
   Обновить даты учтённых родительских каталогов. Затем commit.
5. Только после подтверждения удалить собственный old/new/plan и пустой каталог операции,
   вернуть Success и уведомить UI.

Файловая система и SQL — разные ресурсы. Save использует резервирование и два rename,
не одну атомарную общую транзакцию: внешний процесс может кратковременно увидеть
отсутствие имени/ошибку sharing. Старые байты не перезаписываются частичной записью.
При заполнении диска/занятом файле/ошибке аудита успех не возвращается.

## Сбои и восстановление

При известном SQL rollback опубликованный новый объект удаляется **только** при совпадении
с записанной версией/identity; old возвращается без перезаписи. Если внешнее изменение
не совпадает с журналом, ничего не уничтожается, остаётся RecoveryRequired.

При неопределённом ответе commit проверяется успешный FILE_TX_* с тем же CorrelationId
и UserId. Если SQL недоступен, сохраняются plan/backup, новые команды заблокированы.
Нельзя делать слепой retry и откатывать уже committed данные. Даже после подтверждения
неопределённого ответа UI получает необходимость обновления, а не ложный Success.

«Восстановить» проверяет journal по существующей SQL:
- подтверждён FILE_TX_* — завершить очистку, сохранить опубликованный объект;
- успех отсутствует при доступной БД — восстановить исходный объект;
- изменён объект/повреждён plan/БД недоступна — оставить артефакты и показать ошибку.

Папка без полного плана (например, аварийное завершение прямо во время подготовки),
непонятные служебные файлы и внешние изменения не очищаются автоматически.
Нужны резервная копия/ручной анализ; нельзя удалять .sfm-internal «для починки».
Устойчивость к любому отключению питания/сбою контроллера или злонамеренному редактированию
журнала владельцем Windows не гарантируется. Журнал не является резервной копией.

## Рассинхронизация

Список объединяет физические непосредственные объекты и scoped SQL записи:
Учтён / Вне БД / Изменён / Отсутствует / Недоступно (unsafe).
Новые внешние файлы автоматически не становятся записями Files.
«Сверить» после подтверждения пользователя:
- явно учесть допустимый объект текущего корня;
- обновить известный размер/mtime;
- пометить отсутствующий объект soft-deleted, не удаляя физические данные.

Изменение типа объекта требует ручного разбора. Старые даты, несовместимые с CreatedAtUtc,
отклоняются вместо переписывания истории. Папку с отсутствующими детьми можно открыть
как логический каталог, сверить записи детей и затем сам каталог.
Физическая пустота и отсутствие активных потомков SQL обязательны для удаления папки.
Рекурсивного удаления пользовательских каталогов нет.

Список сравнивает размер/mtime; одинаковые размер/mtime не доказывают неизменность байтов.
Read выдаёт SHA-256 + identity/mtime/size и RowVersion в непрозрачной версии редактора.
Save проверяет их заново; старый редактор и внешний writer не затирают новую версию.

## Импорт

Разрешён поручением пользователя этапа 05 как узкое read-only исключение:
один явно выбранный локальный файл, текущие Windows-права, без исполнения/перемещения/
удаления источника. UNC/device/network paths, ADS, reparse chain, hard links и ярлыки
.lnk/.url/.website не допускаются. Любой источник внутри **всего** Storage отвергается,
чтобы выбор файла другого app-пользователя не обходил ownership.
Внешние каталоги не сохраняются как доступные расположения и не просматриваются дальше.

Назначение — текущий проверенный относительный каталог A, имя не конфликтует с SQL/диском.
Импорт считается FILE_CREATED с Details=FILE_TX_Import; абсолютный источник не записывается
в Operations или JSON plan. В VM передаётся opaque selection, path не отображается/логируется.

## Лимиты и дальнейшая работа

TXT UTF-8 strict — 10 МиБ; BOM UTF-8 читается, NUL/ошибки декодирования отклоняются.
Другие форматы показывают сведения, не открываются в ОС. Импорт — 100 МиБ,
список — 10000 объектов, RelativePath — 400 UTF-16 символов, имя — 255,
расширение метаданных — 32. Пагинация и полноценный JSON/XML/ZIP не реализованы.

Windows ACL, фактическое отсутствие места и power loss не воспроизводились разрушительно;
IO/SQL failures, rollback, interrupted publish, ambiguous commit, junction/hard link,
rename pinned ancestor проверены изолированно. Отдельную file symlink создать в доступном
окружении не удалось; все reparse flags отвергаются тем же правилом, но это не отдельный
положительный тест symlink. Native GUI/DPI/диалоги требуют ручной приёмки.

## Актуализация этапа 06

Прежние ограничения «только TXT» выше относятся к снимку этапа 05. Теперь тот же сервис
читает/создаёт/сохраняет TXT/JSON/XML (UTF-8 strict, 10 МиБ для всех трёх, включая BOM).
Создание JSON/XML задаёт минимальный корректный документ. Save валидирует структуру до Stage.
BOM сохраняется по исходному handle, текст/переводы строк автоматически не форматируются.
Reload — явная команда перечитывания и обновления метаданных с обязательным аудитом;
UI подтверждает потерю буфера и заменяет его только после успеха. Конфликт не даёт force overwrite.
JSON_VALIDATED/XML_VALIDATED дополняют прежний FILE_UPDATED, отдельного журнала/SQL схемы нет.
Парсеры/лимиты/тесты/ручная приёмка описаны в DECISIONS.md и STAGE06_REPORT.md.

## Актуализация этапа 07

ZIP-команды обслуживает тот же FileService/Run/SQL/Windows workspace. StageGenerated готовит
один архив либо целое дерево в прежнем private new. Extract публикует только НОВУЮ папку
одним rename; merge/overwrite запрещены. Tree в плане фиксирует каждый относительный узел
и его версию, plan <=1 МиБ, <=250 выходных узлов. Проверка всего дерева предшествует
rollback-delete; все проверяемые handles удерживаются до удаления. Неожиданное изменение
даёт RecoveryRequired, а не слепую очистку. Исходные пользовательские файлы не удаляются.

Успех ZIP_CREATED/ZIP_EXTRACTED имеет FILE_TX_* и тот же CorrelationId, поэтому прежнее
восстановление разрешает неопределённый SQL commit. Новые Files всего дерева и аудит
фиксируются одной SQL-транзакцией. Сбой после publish компенсируется, неподтверждённый
commit сохраняет артефакты. Incomplete plan/ошибка cleanup требуют ручного разбора, не удаления .sfm-internal.

Потоковый ZipEngine использует 64 КиБ, strict Windows entry-path policy, preflight заголовков,
лимиты 250/25 МиБ/100 МиБ/100:1, фактические байты/длину/CRC. Preview не извлекает данные.
Store/Deflate читаются, создание — Store; ZIP64/encrypted/multipart не поддерживаются.
Симлинки/special entries и физические reparse/hard links отвергаются. Безопасность от
привилегированного локального обхода и любого power loss не обещается.
Полный алгоритм, тесты и ручная инструкция — STAGE07_REPORT.md / STAGE07_MANUAL_TEST.md.
