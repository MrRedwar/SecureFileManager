# Ручная приёмка этапа 04

Дата подготовки: 01.11.2026. Эти сценарии **ещё не пройдены вручную**.
Автоматические доказательства и ограничения — STAGE04_REPORT.md.

## Подготовка и запуск

1. Открыть существующее SecureFileManager.sln в VS 2022, выбрать Wpf как startup project,
   Debug. Не менять TFM и не пересоздавать решение.
2. В локальном профиле запуска/окружении отладчика задать SFM_ENVIRONMENT=Development,
   SFM_CONFIG_DIRECTORY=D:\SecureFileManager\src\SecureFileManager.Wpf. Использовать уже
   настроенный игнорируемый appsettings.Development.json с Windows Authentication.
   Не копировать строку подключения в launchSettings.json под Git.
3. В Development разрешены Encrypt=True;TrustServerCertificate=True только для локального
   SQL Express. Production требует проверки сертификата. TLS не отключать.
4. Для приёмки выбрать выделенную **новую** БД и отдельный локальный корень хранения.
   Не использовать рабочие данные для опытов с отказами. По умолчанию файлы размещаются
   в %LOCALAPPDATA%\SecureFileManager\Storage\Users\{UserId}\; для тестовой среды задать
   SFM_STORAGE_ROOT абсолютным путём отдельной тестовой папки вне Git. Не указывать
   корень диска, UNC, junction или сетевой накопитель. Не менять корень между входами.
5. К новой БД применить обе миграции командой ниже, после проверки имени/отсутствия данных.
   Для существующей рабочей базы новая миграция уже применена. Не откатывать её.

```powershell
dotnet tool restore
dotnet ef migrations list --project src/SecureFileManager.Data --startup-project src/SecureFileManager.Data
dotnet ef database update --project src/SecureFileManager.Data --startup-project src/SecureFileManager.Data
```

Для запуска без изменения общих профилей VS из PowerShell в корне проекта:

```powershell
$env:SFM_ENVIRONMENT = 'Development'
$env:SFM_CONFIG_DIRECTORY = (Resolve-Path src/SecureFileManager.Wpf).Path
dotnet run --project src/SecureFileManager.Wpf
```

## Сценарии приёмки

- [ ] При старте открывается только окно входа. Статус БД появляется после проверки;
  «Повторить» заново проверяет подключение. Главное окно без входа не открывается.
- [ ] Переключить вход/регистрацию. Tab/Shift+Tab дают видимый фокус, Enter отправляет
  активную форму. На регистрации при малой высоте доступна прокрутка ко всем полям
  и кнопке; фокусируемый элемент попадает в видимую область.
- [ ] Зарегистрировать A и B с самостоятельно выбранными логинами/паролями. Не записывать
  пароли в отчёт. Проверить валидацию логина 3–50, пароля 10–128, несовпадения подтверждения.
  Повтор того же логина и варианта другого регистра отклоняется.
- [ ] Регистрация сообщает успех и возвращает к входу, но не создаёт сессию автоматически.
  Оба GUID-каталога существуют и различаются; в Users нет открытого пароля. Не выводить
  хеши в скриншоты и отчёты; их формат/проверка уже проверены автоматически.
- [ ] Неверный пароль и неизвестный логин дают «Неверный логин или пароль».
  После пяти ошибок правильный пароль тоже отклоняется. Через 15 минут вход разрешается;
  не менять системные часы — временные границы отдельно проверены тестовыми часами.
- [ ] При запросе кнопка недоступна, повторный Enter не дублирует запрос, виден прогресс.
  Поля пароля очищаются после отправки и при переходе на другую форму.
- [ ] Войти A. В боковой панели/футере/настройках его реальный логин. Все шесть разделов
  открываются в одном главном окне. Действия этапов 05+ остаются недоступными.
- [ ] Переключить раздел, ввести текст в доступные поля каркаса, затем «Выйти».
  Главное окно закрывается, появляется новая форма входа с пустыми паролями/логином.
  Войти B в том же процессе: нет состояния и данных A, стартовый раздел — «Мои файлы».
- [ ] Закрытие главного окна завершает сессию и приложение; не появляются дополнительные
  окна. Окна входа/регистрации корректно сворачиваются, разворачиваются и закрываются.
- [ ] Проверить главное окно 1440×900 и 1024×640 DIP, формы 640×760 и 520×600 DIP,
  Windows 100%/150%. На 150% учитывать доступную рабочую область экрана. Проверить русский
  текст, фокус, длинный логин, отсутствие перекрытий и работоспособность прокрутки.
- [ ] В SSMS проверить Users и Operations (без вывода хеша). Для рабочей базы доступен
  docs/sql/verify-stage04.sql; для выделенной тестовой базы сначала адаптировать его
  проверку DB_NAME явно к выбранному тестовому имени. Есть LOGIN_SUCCESS, LOGIN_FAILED,
  LOGOUT; для неизвестного логина UserId/FileId NULL, время UTC. Чужие ID/пути,
  ACCESS_DENIED и отказ аудита проверены изолированными интеграционными тестами.
- [ ] Проверить недоступность БД только в тестовом профиле, указав отсутствующую тестовую
  БД; не останавливать общий сервер и не удалять базу. Диагностика безопасна, входа нет.
  Вернуть локальную конфигурацию после проверки. Ошибки каталога также проверять
  исключительно в выделенном корне, не изменяя ACL/содержимое рабочих папок.

## Автоматические проверки

```powershell
$env:SFM_RUN_SQL_TESTS = '1'
$env:SFM_ENVIRONMENT = 'Development'
dotnet restore
dotnet build SecureFileManager.sln -c Debug
dotnet test SecureFileManager.sln -c Debug
```

SQL-тесты сами создают уникальную SecureFileManagerTests_GUID и временные каталоги,
не удаляют их после выполнения. Тестовые SQL-триггеры удаляются только из этой БД.
Повторный прогон создаёт другую БД. Без SFM_RUN_SQL_TESTS=1 SQL-тесты пропускаются —
такой прогон не считается полноценной проверкой этапа.

После ручного прохождения записать фактический результат в PROGRESS.md и завершить
04.07 в TASKS.md. Этап 05 и Git-коммит требуют отдельного разрешения.
