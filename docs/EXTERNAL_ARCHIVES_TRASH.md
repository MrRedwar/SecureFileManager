# 11.04 — Корзина приложения и внешние ZIP

Дата: 07.11.2026. База изменений: `c51c09e` (11.03), исходное рабочее дерево чистое.
Статус: реализация и автоматические проверки готовы; ручная приёмка новых команд NOT RUN.
Пользователь подтвердил обычную проверку 11.03 сообщением «я протестировал и вроде норм».
Это не подтверждает отдельные DPI/keyboard/clean-install сценарии прежних этапов.

## Использование

Открыть «Диски → Файлы компьютера», перейти в разрешённую внешнюю папку.
Все действия находятся в прежнем компактном меню «Действия», тема и шесть разделов сохранены.

| Команда | Действие |
|---|---|
| В корзину приложения… | Выбрать файл/папку, проверить исходный путь, подтвердить. Объект исчезает из списка, байты сохраняются на том же томе. |
| Восстановить удалённое по пути… | Ввести полный **исходный** путь, включая имя. Подтвердить. Путь должен быть свободен, родитель должен существовать. |
| Создать ZIP… | Выбрать один файл или папку с потомками, выбрать папку назначения и имя `.zip`, подтвердить. |
| Содержимое ZIP… | Выбрать ZIP; показаны реальные записи, заявленные размеры и предупреждения. Это ещё не проверка CRC распакованных байтов. |
| Распаковать ZIP… | Выбрать ZIP, изучить preview, подтвердить, выбрать назначение и имя **новой** папки, подтвердить итоговые пути. |
| Проверить операции | Проверить незавершённые планы по корреляции SQL: завершить подтверждённое или отменить неподтверждённое. |

Корзина приложения отличается от Корзины Windows. Подключение Shell recycle не добавлено:
его внешнее перемещение нельзя откатить прежним handle/SQL-протоколом. Используется
обратимое переименование без перезаписи. Внешнего безвозвратного удаления и автоматической
очистки нет; место на диске при помещении в корзину **не освобождается**.

Пример только для отдельной учебной папки: создать `demo.txt`, записать его полный путь,
поместить в корзину приложения, восстановить по записанному пути. Рабочие пользовательские
документы для проверок не нужны. Не удалять `.sfm-*`, служебные планы и квитанции вручную.

## Компоненты и данные

Расширен существующий ExternalFileOperationService: Delete/Restore/CreateZip/ExtractZip
и PreviewAsync. WindowsExternalOperationStorage остаётся единственным адаптером операций;
добавлен partial ArchivesTrash. ZipEngine переиспользован без изменения его защит.
ComputerBrowserViewModel получает пять команд, WindowsFileDialogs использует настоящий
ArchivePreviewWindow и прежние диалоги имён/выбора папки/подтверждения (No по умолчанию).

Схема EF **не менялась**, новых пакетов и миграций нет. Используются ExternalDocuments и
Operations, личные Files/Users не изменяются. При Delete известные внешние метаданные
переносятся на служебный путь с сохранением GUID; при Restore возвращаются вместе с
потомками. Неучтённые файлы регистрируются при успешном результате. IsDeleted к внешней
модели не добавлялся: объект физически сохранён по новому пути. Старые снимки аудита
не переписываются, открытый старый редактор не может сохранить в удалённый/переименованный
объект без повторного чтения версии. Обычное открытие служебного пути запрещено.

Успешные metadata+audit сохраняются в одной Serializable SQL-транзакции с проверкой
активного пользователя и ревизии сеанса. CommittedAsync распознаёт новые фиксированные
коды финального события; source/preview события сами по себе не доказывают commit операции.
Журнал своего пользователя показывает новые русские описания, исходный и целевой снимки.

## Протокол корзины

1. Проверка локального исходного пути, запрет корня тома, личного Storage и его предка,
   pending редактора, ссылок/reparse/hardlink. Закрепление родителей и DELETE handle.
2. Ограниченный snapshot дерева: идентичность, размер, UTC, SHA-256 файлов.
3. Durable plan в `StorageRoot/.external-operations/<id>.json` до изменения имени.
4. No-replace rename в **соседний** `.sfm-trash-<id>` на том же томе. Внешний Windows
   ACL продолжает действовать. Префикс исключён из браузера приложения; это не системный
   атрибут Hidden, шифрование или защита от Windows-владельца/администратора.
5. SQL metadata+audit (`EXTERNAL_OP_Delete`, FILE_DELETED), затем квитанция в
   `StorageRoot/.external-trash/<id>.json`, затем удаление завершённого плана.
6. Restore ищет квитанцию по исходному пути, проверяет неизменность всего дерева,
   переименовывает назад, обновляет metadata+audit (`EXTERNAL_OP_Restore`), удаляет квитанцию.

Неподтверждённое перемещение откатывается только после проверки **всего** дерева и свободного
исходного имени. При неизвестном SQL-результате/посторонних изменениях данные и план сохраняются.
Committed recovery идемпотентно завершает квитанцию/план; восстановить может другой активный
app-пользователь того же экземпляра StorageRoot, если Windows ACL разрешает доступ.
Несколько квитанций для одного исходного пути дают Conflict, выбор поколения в UI пока отсутствует.
Неизвестные/повреждённые квитанции блокируют восстановление, без догадок и стирания данных.

## ZIP и границы безопасности

Архивируется один выбранный файл или дерево, включая бинарные файлы и пустые папки.
ZIP Store/UTF-8 позволяет не создавать архивы, нарушающие собственный ratio limit.
Внутри ZIP сохраняется имя выбранного корня. ACL/специальные атрибуты не архивируются.
Распаковка только в новую папку, без overwrite/merge. Между preview и извлечением
проверяется fingerprint исходного ZIP; замена даёт Conflict. Исходник открыт через safe
handle, родители закреплены; повторный snapshot обнаруживает изменения исходного дерева.

ZipEngine проверяет envelope и central/local headers, абсолютные/drive/UNC/traversal/ADS
пути, reserved names, ссылки, CI-дубликаты, конфликты файл/папка, encryption/ZIP64/multi-volume,
размеры и ratio. Лимиты: 250 записей, 25 МиБ/файл, 100 МиБ распакованных байтов, 100:1.
При извлечении считаются **реальные** байты и CRC; результат сначала пишется в соседний
`.sfm-op-<id>`, закрытые файлы фиксируются по физической идентичности и хешу. Только полностью
проверенное дерево публикуется. При сбое SQL/аудита убирается только собственный неизменённый
результат. Неожиданные данные не удаляются ради очистки. Private Storage/links не становятся
разрешёнными через ZIP. Структурный отказ не создаёт staging; CRC-отказ очищает частичный staging.

Сохраняются дополнительные лимиты внешнего адаптера: 1000 узлов, 100 МиБ на физический
файл, 1 ГиБ/дерево. Поэтому внешний входной/сгенерированный ZIP свыше 100 МиБ отклоняется
операцией, даже если stream preview допускает envelope до 101 МиБ. Архив с входными
данными ровно 100 МиБ может превысить внешний предел из-за ZIP-заголовков.

SQL+NTFS не образуют единой атомарной транзакции; сертификация crash/power-loss durability
не проводилась. Физическая ошибка записи плана/квитанции/очистки может требовать ручного
разбора сохранённых данных. Потеря/ручное изменение квитанций, перенос StorageRoot или
изменение корзины через Windows не исправляются автоматически. Нет обхода ACL, защиты
от прямого доступа администратора Windows/SQL, освобождения места корзиной и фоновых служб.
UI показывает indeterminate progress, отдельная кнопка отмены новых команд не добавлена.

## Ручная приёмка новых команд — NOT RUN

Использовать отдельную пустую внешнюю учебную папку и данные из demo.

1. Создать TXT и вложенную папку с бинарным файлом/пустой подпапкой. Записать полные пути.
2. Поместить TXT/дерево в корзину приложения; проверить подтверждение и исчезновение из списка.
3. Восстановить по исходному пути, сверить байты/папки. Повторить при занятом исходном имени:
   должен быть конфликт без перезаписи. Не очищать рабочие каталоги.
4. Создать ZIP выбранного дерева в соседней учебной папке. Показать реальный preview.
5. Распаковать в новую папку, проверить результат. Повторить с существующим именем:
   отказ без merge. Отмена каждого диалога не должна изменять файлы.
6. Проверить собственный журнал: FILE_DELETED/FILE_UPDATED/ZIP_CREATED/ZIP_EXTRACTED,
   понятные описания и пути. Сменить app-пользователя, повторить обычный общий доступ.
7. Проверить новые пункты меню клавиатурой и отсутствие перекрытий при 1024×640,
   1440×900, Windows 100%/150%. Не останавливать рабочую SQL-службу ради демонстрации.
