## Использование

Войти → «Диски → Файлы компьютера» → открыть папку → меню **«Действия»**.

| Команда | Поведение |
|---|---|
| Создать файл | Имя с расширением; TXT/прочие типы пустые, JSON `{}`, XML `<document />` |
| Создать папку | Создаётся новая пустая папка |
| Копировать в… | Выделить один файл/папку, выбрать папку назначения и имя, подтвердить |
| Переместить в… | Аналогично, перемещение на том же локальном томе |
| Переименовать | Новое имя в текущей папке, с подтверждением |
| Проверить операции | Сверить сохранённые планы с SQL и завершить/компенсировать известный результат |

Папки копируются с вложенностью, бинарными файлами и пустыми папками. Имеющиеся объекты
никогда не перезаписываются, каталоги не объединяются: конфликт требует другого имени.
В корне «Этот компьютер» создание недоступно, сначала выбрать диск/папку. После успеха
список обновляется. Команды работают асинхронно. Данные принадлежат общему внешнему
пространству по Windows ACL, а не app-пользователю, впервые открывшему объект.

**Ограничения11.03:** move/rename только в пределах одного тома; между томами доступно
копирование с сохранением исходника. Case-only rename не поддержан (считается конфликтом).
Один выбранный объект за команду; предел дерева1000 узлов,100 МиБ на файл,1 ГиБ суммарно.
Лимиты проверяются перед обработкой и на фактически копируемых байтах. Не включены
сеть/UNC/device/ADS, reparse/junction/symlink/hardlink и операции внутри личного Storage.
Префикс `.sfm-` зарезервирован, служебные staging-каталоги не показываются браузером.

## Архитектура и БД

Core: ExternalChangeRequest/ExternalOperationPlan/ExternalOperationEntry,
IExternalFileOperationService/ExternalFileOperationService и инфраструктурные порты.
Wpf/Infrastructure: WindowsExternalOperationStorage использует прежние Native handles,
проверку абсолютных локальных путей и PersonalStorage boundary. VM/Views не выполняют IO.
WindowsFileDialogs предоставляет имена/назначение/подтверждение; компактное меню
не увеличивает число основных разделов приложения и сохраняет оформление.

Переиспользованы ExternalDocumentStore и существующая схема из11.02.
**Новой миграции нет**, рабочую БД повторно обновлять не требуется.
ExternalDocuments хранит общие метаданные файлов; папки отдельными строками этой
таблицы не представляются, но имеют собственный абсолютный снимок цели и тип события.
AppDbContext допускает external snapshot без document FK только для фиксированных
кодов операций11.03; прежние правила личного FileId/owner и пути не ослаблены.

При create/copy регистрируются итоговые файлы с фактическими size/mtime/fingerprint;
копия исходного документа получает отдельную запись. При move/rename учтённые файлы
и потомки переносятся на новые Path/PathKey с сохранением их GUID и audit history.
Открытый старый редактор получает version/RowVersion conflict, его буфер не затирает
перенесённый файл. Явное перечитывание загружает новый путь/имя/формат того же GUID.
Модель по-прежнему учитывает только известные приложению файлы, не индексирует весь ПК.

Metadata и success audit фиксируются одной Serializable SQL-транзакцией под active-user
lock. Session/revision проверяются в сервисе до/после await. Корреляция результата общая
для всех app-пользователей, committed save не откатывается при восстановлении другим actor.
Автоповтора файлового callback нет. При недоступной БД новые файловые операции не начинаются.

| Код Details | Тип / объект |
|---|---|
| EXTERNAL_OP_CreateFile | FILE_CREATED, конечный файл |
| EXTERNAL_OP_CreateDirectory | DIRECTORY_CREATED, конечная папка без фиктивного FileId |
| EXTERNAL_OP_Copy | FILE_CREATED, корень новой копии |
| EXTERNAL_OP_Move | FILE_UPDATED, новое расположение |
| EXTERNAL_OP_SOURCE | FILE_READ, снимок исходного пути copy/move |
| EXTERNAL_OP_RECOVERED | FILE_UPDATED, проверка восстановления |

JournalService отдаёт только собственный actor scope и разрешённые коды/валидные пути;
новые снимки видны и доступны поиску. В Details нет содержимого/сырого exception.
Ошибки/отказы сохраняются фиксированным EXTERNAL_OPERATION_<status>, success не выдаётся
без подтверждённых metadata+audit. При отказе самого аудита запись не обещается.

## Физический протокол и сохранность

1. После проверки SQL/session открывается workspace с единым межпроцессным lock в
   StorageRoot/.external-operations. Неизвестный/незавершённый план блокирует новые команды.
2. Проверяются имена, абсолютные пути, private boundary, отсутствие конфликтов и
   self-copy/перемещения в собственное поддерево. Все физические предки pin-ятся.
   Ссылки/чужие namespace не обходятся, root диска не является допустимым источником move.
3. Create/copy готовятся в новом `.sfm-op-<GUID>` рядом с назначением. CreateNew и
   CreateDirectoryW без режима reuse предотвращают присвоение существующего объекта.
   Поток64КиБ, реальные byte budgets, Flush(true); план содержит состав дерева,
   directory identities и file identity/size/mtime/SHA-256. Источники сверяются повторно.
4. Ограниченный plan.json (<=1МиБ) записывается CreateNew+Flush до публикации. Подготовленное
   дерево публикуется одним no-replace rename. Move/rename использует исходный native
   DELETE handle, сохраняя identity/ACL; читающий/пишущий редактор либо иная занятость
   дают отказ вместо перезаписи. Копия наследует ACL назначения, специальные атрибуты
   и исходные timestamps/ACL специально не восстанавливаются.
5. Затем общие файловые метаданные и аудит коммитятся. При известном rollback удаляется
   только собственный полностью совпавший новый результат; move переименовывается обратно.
   Перед очисткой проверяется всё дерево, его состав/версии, объекты открываются handles.
   При подготовительном отказе/отмене очищаются только совпавшие собственные staging-объекты.
6. При неизвестном commit сервис проверяет correlation+target в SQL. Pending-планы
   сохраняются при недоступности SQL или несовпадении данных. «Проверить операции»
   завершает committed либо компенсирует uncommitted. Неизвестные файлы/изменённые байты
   не удаляются ради уборки. Активный pending11.03 блокирует также внешний редактор;
   незавершённый editor-plan11.02 не разрешает копировать/перемещать соответствующий источник.

SQL+NTFS не являются одной атомарной транзакцией. Промежуточные состояния/сбой питания
не исключены, полная power-loss durability не заявляется. Частичная ошибка cleanup
может потребовать ручного разбора плана; не удалять `.external-operations` вручную.
Уничтожать пользовательские исходники при конфликте/отказе не требуется. Прямой доступ
Windows/SQL администратора, владельца процесса/того же Windows token вне модели защиты.
Изменение прав/повышение привилегий/фоновые службы не добавлены. Системные каталоги
подчиняются фактическим Windows ACL; программа не обещает доступ к любому файлу ОС.

   и произвольный пустой файл, проверить список и редактор.
2. Копировать файл и папку с вложенностью/пустой папкой в другое внешнее место;
   подтвердить путь/имя, сравнить копию и неизменённый источник.
3. Переименовать и переместить demo-файл/папку на том же томе; проверить новые пути,
   идентичность данных, журнал исходной и конечной цели.
4. При открытом demo-редакторе переименовать файл: старое save не затирает данные,
   подтверждённый reload показывает новое имя/формат. Несохранённый буфер сохраняется.
5. Повторное имя/существующая папка/self-copy дают отказ без перезаписи. Отмена picker/
   имени/подтверждения не начинает операцию. Межтомный move даёт понятное ограничение.
